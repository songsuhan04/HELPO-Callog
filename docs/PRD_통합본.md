## 한 줄 소개

독거 고령자(어르신)가 매일 간단한 안부 체크(지병 관련 체크, 컨디션, 음성 답변)를 남기면 AI가 인지기능 저하 등 이상 신호를 조기에 감지해 자녀(보호자)에게 위험도에 따라 알리고, 영상 편지로 정서적 연결까지 함께 유지하는 조기 감지 서비스.

## 문제정의

독거 고령자는 혼자 지내는 시간이 길어 돌봄 공백이 생기기 쉽고, 본인이나 자녀 모두 평소와 다른 이상 신호(특히 인지기능 저하처럼 스스로 알아차리기 어려운 변화)를 조기에 판별하기 어렵다. 자녀는 생업 등의 이유로 매일 방문·통화하기 어렵고, 고령자 본인도 초기 변화를 자각하지 못하는 경우가 많아, 문제가 뚜렷해진 뒤에야 뒤늦게 발견되는 경우가 많다.

### 디지털 활용·가족 소통 수준 기준 세분화 — "디지털 중위 활용층" 타겟 (3차 개정: 명칭 변경)

독거 고령자를 **휴대폰 등 디지털 기기 수용도**와 **자녀와의 소통 수준**을 기준으로 상/중/하 3단계로 나눴을 때, 이 서비스는 중간 계층 — 팀에서 확정한 명칭으로는 **"디지털 중위 활용층"**을 타겟으로 한다.

| 계층 | 특징 | 타겟 여부 |
|---|---|---|
| 상 | 휴대폰 등 문명을 매우 잘 받아들이고, 이미 영상통화 등으로 자녀와 소통이 매우 잘 되는 분들 | ✗ (이미 자녀와 직접 소통이 원활해 조기 감지 서비스의 효용이 낮음) |
| **디지털 중위 활용층** | 휴대폰을 어느 정도 사용할 수 있고, 자녀와도 어느 정도는 소통이 가능한 계층 | **✓ 메인 타겟** |
| 하 | 휴대폰을 아예 사용하지 못하거나, 국가적 도움을 받으며 자녀와 소통 자체가 단절된 분들(보호자가 국가 지원이거나 휴대폰이 없는 수준일 수 있음) | ✗ (앱 기반 온보딩 자체가 불가능 — 국가 복지 서비스 영역) |

**근거**: "상" 계층은 이미 영상통화 등으로 자녀와 활발히 소통하고 있어 별도의 안부 체크·위험 알림 서비스가 주는 부가가치가 작다. "하" 계층은 휴대폰조차 다루기 어렵거나 이미 국가 지원 체계에 있어, 앱을 통한 링크 접속·음성 응답 자체가 기술적으로 불가능에 가깝다. Callog(콜록)은 "휴대폰은 어느 정도 쓸 수 있지만 자녀와의 소통은 충분하지 않아 돌봄 공백이 생기는" 디지털 중위 활용층에서 가장 큰 가치를 만들어낸다.

**영향**:
- **온보딩 난이도**: 디지털 중위 활용층 기준으로 설계 — 지나치게 복잡한 기술 조작(다단계 인증, 세밀한 설정)은 피하고, 초대 링크 클릭만으로 접속 가능한 현재 흐름이 이 타겟에 적합하다.
- **문항/UX 톤**: 자녀와의 소통이 "어느 정도는" 되는 계층이므로, 완전히 소통이 단절된 취약계층 대상 문구(과도하게 보호적인 톤)보다는 일상적인 안부 확인 톤을 유지한다.
- **접근성 기능**(글씨 크기 확대, TTS)은 유지하되, "하" 계층(비휴대폰 사용자)까지 포괄하는 것을 목표로 하지 않는다 — 이는 범위 밖으로 명확히 한다.

## 가족 구조 — 1가족 : N어르신 (확정)

기존 3강 워크시트는 "1고령자-1가족 단위로 한정, 다대다 구조는 다루지 않는다"고 정의했으나, 8/12 데모의 대상자 목록 화면은 이미 보호자 1인이 여러 어르신(부모·시부모 등)을 관리하는 화면을 보여주고 있었다. 팀 논의 결과 **1가족(보호자 계정) : N어르신** 구조를 공식 스코프로 확정한다.

- **데이터 모델 영향**: 가족계정 1 — N 어르신프로필 관계로 설계 (상세는 [데이터스키마.md](데이터스키마.md) 참고)
- **알림 라우팅 영향**: 위험도 알림은 어르신 단위로 발생하고, 대상자 목록 화면에서 여러 어르신을 우선순위(안전/위험/심각)로 한눈에 확인
- **온보딩 영향**: 가족 계정은 "어르신 등록"을 반복 가능한 단계로 취급 — 최초 등록 후에도 "어르신 추가" 흐름으로 계속 인원을 늘릴 수 있다

## 차별점 (회의에서 강조된 포지셔닝)

- 기존 서비스는 복지 정보 안내·응급 알림·돌봄 신청처럼 기능이 분절되어 있으나, Callog(콜록)은 건강과 주거 신호를 함께 보고 위험 신호를 먼저 찾아내 보호자가 바로 이해할 수 있는 화면으로 연결한다.
- **카카오톡 같은 범용 메신저 대비**: 지병 맞춤 질문 + 자동 위험도 산정 + 보호자용 우선순위 대시보드가 구조화되어 있어, 매일 직접 챙기지 않아도 이상 신호만 걸러서 받을 수 있다.
- **"진단이 아니라 확인"** — AI는 진단을 내리지 않고 확인이 필요한 변화만 짚어준다. 법적·신뢰 리스크를 최소화하면서 부담 없는 톤을 유지하는 것이 핵심 포지셔닝이다.
- **이름 자체가 차별점**: 서비스명 "Callog(콜록)"은 "Call"(안부를 묻는 통화·연락)과 "Log"(매일 쌓이는 기록)을 합친 이름으로, 매일의 안부 체크가 곧 하나의 기록으로 남는다는 서비스의 핵심 가치를 그대로 담는다.

### 경쟁 서비스 비교

| 서비스 | 기능 | 타겟 | 가격 | Callog(콜록) 대비 차별점 |
|---|---|---|---|---|
| 카카오톡(영상통화) | 범용 메신저·영상통화 | 전 연령 | 무료 | 구조화된 안부 체크·위험도 산정·우선순위 알림이 없음. 보호자가 매번 직접 확인해야 함 |
| 지자체 안부확인 서비스 (독거노인 안심콜 등) | 전화 기반 정기 안부 확인, 응급 연계 | 국가 지원 대상 고령자 | 무료(공공) | 응급 신고·전화 중심이라 정서적 연결(영상편지) 요소가 없고, 보호자에게 직접 데이터가 공유되지 않음 |
| 민간 케어콜 서비스 | AI 전화 콜, 간단 안부 질문 | 유료 가입 고령자 | 유료 | 음성 통화 중심으로 지병별 맞춤 질문이나 보호자용 대시보드가 약함 |
| 복지로(정부 포털) | 복지 정보·신청 창구 | 전 국민 | 무료(공공) | 정보 안내 중심으로 실시간 이상 신호 감지 기능 자체가 없음 |
| **Pascal(ORA)** — 직접 경쟁사 (2026-08-27 추가) | AI가 먼저 전화를 걸어 안부 확인, 방언·느린 말투 인식 특화, 일간·주간·월간 종합 리포트(건강·감정·위험도) | 보호자(B2C) + 기관(B2B) + 공공 3트랙, 실제 등록 법인(사업자번호 보유) | 비공개(문의제) | AI가 "먼저 전화를 거는" 수동적 구조라 어르신이 응답만 함. 리포트 중심이라 정서적 상호작용 채널이 없음 — Callog는 어르신이 스스로 안부를 "남기는" 능동적 구조 + 영상편지로 정서적 연결까지 포함 |

Callog(콜록)은 "지병 맞춤 질문 + 위험도 산정 + 보호자 대시보드 + 정서적 영상편지"를 하나의 흐름으로 묶은 유일한 조합이라는 점이 차별점이다. 다만 Pascal(ORA)은 이미 사업자 등록을 마치고 B2C·B2B·공공 3트랙 사업모델까지 갖춘 실제 운영 서비스로, 전화 기반 온보딩(설치·링크 불필요)이라는 강력한 마찰 최소화 강점을 가진 가장 근접한 직접 경쟁사다. 심사·투자자 질문에서 이 비교가 나올 가능성이 높으므로 [케이스 스터디](case_study.md) 및 발표 대본의 대응 논리를 숙지할 것.

## 핵심 가치

- 어르신 본인이 매일 짧은 시간만 투자해 안부를 남기면, AI가 사람이 놓치기 쉬운 이상 신호를 조기에 감지한다.
- 보호자는 매일 직접 확인하지 않아도, 위험도가 실제로 높아졌을 때만 단계적으로 알림을 받는다.
- 영상 편지 기능으로 어르신과 보호자 사이의 정서적 연결을 함께 유지한다.
- AI는 진단을 내리지 않는다. 확인이 필요한 변화를 먼저 짚어주는 역할에 머문다.

## 핵심 기능 (MVP 확정, 4강 코칭 + 3차 개정 반영)

1. **일일 안부 체크**: 등록된 지병 목록 기반 맞춤 체크리스트 6~8문항 (선택형 응답)
2. **말하기 안부**: 자유 음성 1문항(보호자에게 한마디, 매번 무작위 주제) — **Gemini API**로 음성을 직접 분석해 발화 속도·침묵 비율 등 인지기능 신호 후보를 산출. TTS로 질문을 읽어주어 거부감 완화 (※ 기존 STT API + 규칙기반 방식에서 Gemini 활용으로 변경, [기능설계서.md](기능설계서.md) §0·§2.2 참고). **(5차 개정: 구현·실사용 검증 완료** — 자세한 내용은 [오픈 이슈 6번](#오픈-이슈-다음-회의에서-확정-필요) 참고)
3. **위험도 분석 및 알림**: 지병별 가중치 + 무응답 시간/복약 누락/연속 외출 없음 등을 근거로 안전·위험·심각 3단계 산정. 경미한 변화는 알림만, 심각한 변화는 알림+대응 안내(직접 신고는 하지 않음). **(5차 개정: `lib/riskScoring.ts`에 실제 구현 완료** — 단, 실제 채점은 체크인 응답 심각도 중심이며 "무응답 7시간·연속 외출없음 3일" 같은 시간 기반 임계값은 아직 코드에 반영하지 않았다)
4. **영상 편지**: 어르신·보호자 상호 교환. 안부 체크를 완료해야 그날 도착한 편지가 열리는 구조로 꾸준한 참여를 유도. 발신 후 7일이 지나면 자동 삭제(Vercel Cron). (**5차 개정**: Gemini 영상 분석은 도입하지 않기로 최종 결정 — 저장·재생만 제공. 근거는 [오픈 이슈 5번](#오픈-이슈-다음-회의에서-확정-필요) 참고)
5. **초대 링크 기반 온보딩**: 어르신은 앱 설치·계정 생성 없이 1회용 링크(기기당 1회 개봉 후 만료)로 접속. (**5차 개정**: 보호자 본인 계정은 이메일+비밀번호로 즉시 가입한다. 당초 계획한 이메일 OTP 인증은 Resend 샌드박스 제약으로 제거했다 — 자세한 내용은 [오픈 이슈 7번](#오픈-이슈-다음-회의에서-확정-필요) 참고)

## 사용자 흐름

1. 보호자가 이메일로 계정을 만들고 어르신 정보·지병을 등록한다 (어르신은 반복 등록 가능, 1가족:N어르신).
2. 지병에 따라 자동 구성된 초대 링크를 어르신에게 문자로 보낸다.
3. 어르신이 링크로 접속해 매일 체크리스트+음성 답변을 남긴다.
4. Gemini 기반 분석이 체크리스트·음성 데이터를 과거 기록과 비교해 위험도를 산정한다.
5. 위험도에 따라 보호자에게 단계적으로 알림이 가고, 보호자는 확인·전화·방문 등으로 대응한다.
6. 안부 체크와 별개로 언제든 영상 편지를 주고받는다.

## MVP 범위 확정 (4강 워크시트 · MVP 범위표 기준, 3차 개정 반영)

### 필수 (이번에 만든다)
- 접근성: 글씨 크기 확대 가능 기능, 어르신 눈높이 단어 사용
- 계정/온보딩: 로그인 및 자동 로그인 체크박스, 계정 만들기(이메일→비밀번호→어르신 정보→지병 선택 — **5차 개정: 이메일 인증 단계는 Resend 제약으로 제거, 이메일+비밀번호 즉시 가입으로 변경**), 비밀번호 확인, 계정 찾기, 초대 링크를 통한 가족 연결, **어르신 추가(반복 등록, 1:N 구조)**
- 내비게이션: 모든 선택지에 뒤로가기 버튼
- 안부 체크: 지병 선택에 따라 질문 선택지가 달라짐, 맞춤 질문 음성 응답(6~8개), 응답은 정해진 선택지 기반
- 영상 편지: 주제를 제시하는 방식으로 시작(주제 여러 가지), 확인 후 전송, 촬영 안내 멘트, 마지막 홈버튼
- 대상자 관리: 어르신 정보(**생년월일로 확정** — 화면에는 계산된 나이를 표시하되 저장은 생년월일 기준), 앓고 있는 병(사전 정의 칩 + **직접 입력 1줄 텍스트** 확정), 초대하기 버튼, 대상자 목록 우선순위 표시(안전/위험/심각 구분), 목록에서 관계 또는 별명 설정(※ 관계 필드는 1차 유지, 성별 필드는 **5차 개정: DB 스키마에는 추가했으나 UI 노출 여부는 팀 최종 확인 필요**), 시간 선택 기능
- 기록/차별점: 꺾은선 그래프 기록, 연속 참여 기록, 영상통화 저장/다운로드 기능, 음성과 영상 기능 합치기
- 데이터/보안: 개인정보 동의

### 나중 (아이디어톤 이후)
- 앱/클라우드 제공

### 버림 (하지 않는다)
- AI의 안색 또는 표정 진단 — 개인정보 침해 우려, 조명에 따라 판별이 불가능하여 기술적으로도 신뢰하기 어려움 (⚠️ 3차 개정에서 "Gemini 영상 분석" 도입이 결정됐는데, 이 항목과 상충하지 않는지 팀 확인 필요 — 아래 오픈 이슈 참고)
- 외부 데이터 사용을 줄이는 방향으로 설계 (자체 체크리스트·음성 데이터 중심)
- 자체 ML 모델 학습 — Gemini API 활용으로 대체 (팀 리소스·일정 고려)

## 수익모델 / 지속가능성

**전면 무료 서비스**로 진행한다. 사회문제 해결을 우선순위로 두고, 이번 단계에서는 구독·프리미엄 등 결제 기능을 만들지 않는다. 지자체·복지관과의 협력을 통한 향후 지속가능성 모델은 현재 스코프에서 다루지 않으며, 필요 시 추후 별도 논의한다.

## 구현 현황 (5차 개정 신규)

기획 단계에서 계획한 것과 실제로 코드로 구현된 것 사이의 간극을 없애기 위해, 실제 저장소(`demo/v1`, `api/`, `lib/`) 기준 구현 상태를 정리한다.

- **스택**: React + Vite 프론트엔드(`demo/v1`), Vercel Serverless Functions(`api/*.ts`), Supabase(Postgres + Auth + Storage), Gemini API(음성 분석·질문 생성). PWA 아이콘·매니페스트 추가로 홈 화면 추가(iOS/Android) 지원.
- **19개 화면 전부 구현 완료** — 어르신 7화면, 보호자 7화면, 메인 5화면 모두 실제 라우트(`routes.tsx`)로 존재하며 Supabase에 연결되어 있다(정적 데모가 아님). **(7차 개정)** 비밀번호 찾기·재설정 화면 추가로 13→19 갱신.
- **접근 통제**: Postgres Row Level Security(RLS)로 가족계정·어르신 소유권 기반 접근 정책을 테이블별로 적용. 어르신은 익명 세션(초대 링크 기반), 보호자는 이메일 인증 세션으로 구분하며, 라우트 가드(`ElderRoute`/`GuardianRoute`)로 화면 단위 접근도 통제한다.
- **위험도 산정**: `lib/riskScoring.ts`에 실제 채점 로직 구현 완료 — 응답 심각도 점수 + 고혈압 복약 미준수 1.5배, 당뇨병 결식 2.0배 가중치를 반영해 안전/위험/심각 3단계를 산정한다. **(6차 개정, 2026-08-24 추가)** 두 가중치 모두 동료심사 문헌 근거로 검증했다(당뇨병은 기존 임의값 2.4배에서 문헌 근거 기반 2.0배로 조정 — 자세한 내용은 [위험도가중치 근거자료.docx](../발표%20자료/위험도가중치%20근거자료.docx) 참고). "무응답 7시간"과 "연속 외출없음 3일" 임계값도 이번에 실제로 구현되어, PRD 초안의 임계값이 모두 코드에 반영된 상태다. **(8차 개정)** 무응답 확인 주기를 Vercel Cron(하루 1회)에서 GitHub Actions(매시간, `.github/workflows/check-no-response.yml`)로 변경 — 기존에는 안부 시각 기준 7시간째가 아니라 하루 한 번 몰아서(21:00 KST) 확인해 실제로는 최대 13시간이 걸렸는데, 임계값은 그대로 두고 확인 주기만 고쳐 평균 6시간 더 빨리 감지한다.
- **알림 채널**(7차 개정 신규) — 위험도 산정·무응답·외출없음 감지 결과를 웹 푸시 알림(`lib/sendPush.ts`, 서비스워커)으로 보호자에게 즉시 전달한다.
- **응급 대응 버튼**(7차 개정 신규) — 어르신 화면에 "119에 직접 전화하기" 버튼(`EmergencyCall.tsx`)을 상시 노출한다. 위험도 판정과는 의도적으로 연결하지 않았다 — AI 판단에 응급 대응을 걸면 이용약관의 "응급 상황을 감지하지 않습니다" 면책 조항과 모순되고 책임 소재 문제가 생기기 때문. 오작동 방지를 위한 재확인 절차를 거쳐 기기의 전화 앱으로만 연결한다.
- **보관 기간 및 동의 범위 정정**(8차 개정 신규) — 음성 안부 파일에 30일 보관 기한을 신설(`lib/retention.ts`, 영상편지 7일은 기존과 동일). 음성 파일 삭제 후에도 AI가 받아쓴 내용·소견은 텍스트 기록으로 남는다. 또한 이용약관이 "영상편지도 Gemini로 전송된다"고 잘못 명시하고 있던 것을 발견해 정정했다 — 실제로는 영상편지를 Gemini로 보낸 적이 없어(§ 미구현 항목 참고), 기존 문구는 실제보다 넓은 범위로 동의를 받고 있었다.
- **안부 질문·주제 사전생성 완료**(8차 개정) — PRD 초안에 있던 "매번 무작위 주제"가 실제로는 새벽 3시 크론(`lib/prepareDailyPrompts.ts`)이 그날의 질문·주제를 미리 만들어 `daily_prompt` 테이블에 저장하고, 어르신 화면은 그걸 읽기만 하는 방식으로 완성됐다 — 어르신이 화면을 열 때 AI를 직접 호출해 기다리게 하던 문제(버퍼링)를 없앴다. 영상편지에도 이번에 주제가 추가됐다.
- **안정성 버그 다수 수정**(8차 개정) — 음성 분석 실패 시 그날 기록 자체가 사라지던 문제, 저장 실패 시에도 "완료"로 처리되던 문제, 화면만 열고 나가도 완료로 집계되던 문제, 크론 인증 비밀키 설정 누락 시 인증을 건너뛰고 열려있던 보안 취약점을 모두 수정했다.
- **관리자 대시보드**(신규, PRD 최초 범위 밖) — `gAdmin` 화면에서 화이트리스트 등록된 팀원 계정이 전체 어르신의 위험도 현황을 한눈에 볼 수 있다. 팀 내부 운영·디버깅 목적.
- **디자인**: "알라미(Alarmy) 스타일" 리디자인 적용 완료(다크 테마 기반).
- **미구현/의도적으로 만들지 않은 것**: Gemini 영상 분석([오픈 이슈 5번](#오픈-이슈-다음-회의에서-확정-필요)), 이메일 OTP 인증([오픈 이슈 7번](#오픈-이슈-다음-회의에서-확정-필요)), 위험도 가중치의 임상적 검증([오픈 이슈 2번](#오픈-이슈-다음-회의에서-확정-필요)), AI 기반 응급 상황 자동 대응(의도적 미구현 — 위 응급 대응 버튼 항목 참고).

## 범위 밖

- 의료적 진단·처방은 제공하지 않는다.
- 서비스가 직접 119 등 응급기관에 신고하지 않는다.
- 웨어러블·IoT 센서 연동은 포함하지 않는다.
- 휴대폰을 전혀 다루지 못하거나 자녀와의 소통이 이미 단절된 "하" 계층은 타겟에서 제외한다 (국가 복지 서비스 영역, 앱 기반 온보딩 불가능).
- 유료 결제·구독·프리미엄 기능은 다루지 않는다 (전면 무료 방침).
- 자체 음성 AI 모델 학습은 다루지 않는다 (Gemini API 활용으로 대체).

## 오픈 이슈 (다음 회의에서 확정 필요)

1. **[부분 해결]** 어르신 등록 시 "관계" 필드 유지 + "성별" 필드 추가(제안) — DB 스키마에는 `gender` 컬럼을 nullable로 추가해뒀으나, 화면(UI)에 실제로 노출할지는 아직 팀 최종 확인 전.
2. **[해결]** 위험도 가중치·임계값의 실제 근거 자료 보강 — **(6차 개정)** 동료심사 문헌(IPD 메타분석, INTERHEART 등) 기준으로 검증 보고서를 작성하고, 그 결과에 따라 당뇨병 가중치를 임의값 2.4배에서 문헌 근거 기반 2.0배로 조정(고혈압 1.5배는 기존 값이 문헌 범위와 일치해 유지). "무응답 7시간"·"연속 외출없음 3일" 임계값도 실제 코드에 구현 완료. 다만 흡연·이상지질혈증·복부비만·가족력 등 문헌이 함께 검증한 나머지 위험요인은 현재 지병 목록에 없어 반영 범위 밖으로 남아있다.
3. **[해결]** 영상 편지 녹화 시 안내 멘트·주제 다양화 — `eSpeech.tsx`/`gLetter.tsx`에 무작위 주제 로직을 구현했고, `RecordingNotice` 컴포넌트로 촬영/녹음 화면에 안내 문구를 상시 노출한다.
4. **[해결]** 개인정보 동의 화면의 정확한 위치·문구 — 회원가입 화면(`signup.tsx`)에서 일반 개인정보 동의와 Google(Gemini) 국외이전 동의를 분리했고, 지병 입력 화면(`cond.tsx`)에서 건강 민감정보 동의를 별도로 받는다. `ConsentItem` 컴포넌트의 "자세히" 펼치기로 수집 항목·목적·보유기간을 노출하며, `terms.tsx`(이용약관 화면)에 전체 내용을 통합 정리했다.
5. **[해결]** Gemini "영상 분석"의 정확한 용도 — 논의 결과 **영상 분석 기능 자체를 도입하지 않기로 최종 결정**했다. 어르신의 표정·안색을 분석하는 방향은 이미 "버림" 처리한 항목과 정면으로 충돌하므로 재논의 없이 배제했고, 정서적 톤 분석 방향도 이번 범위에서는 만들지 않는다. 영상편지는 저장(7일 보관 후 자동 삭제)·재생 기능만 제공한다.
6. **[해결]** STT 없이 Gemini만으로 발화 속도·침묵 비율 등 정량 지표 추출 가능 여부 — **실사용 검증 결과 가능**하다고 확인했다. 다만 실제 검증 과정에서 두 가지 실패를 겪었다: ① 사용하던 모델(`gemini-2.0-flash`)이 Google 쪽에서 폐기되어 한동안 모든 호출이 조용히 실패(fallback)하고 있었던 것을 뒤늦게 발견(`gemini-3.6-flash`로 갱신해 해결), ② Gemini가 JSON 응답을 마크다운 코드블록으로 감싸 보내 파싱이 실패하는 문제(방어적 파싱 처리로 해결). 두 문제 모두 "정상 동작처럼 보이지만 실제로는 실패 상태로 조용히 넘어가는" 유형이라, 이후 실패 시 상태값을 명시적으로 기록하도록 코드를 함께 수정했다.
7. **[방향 전환으로 해결]** 이메일 인증 전환에 따른 UX 설계 — 애초 계획한 **이메일 OTP 인증 자체를 제거**했다. Resend가 샌드박스 모드에서는 계정 소유자 본인 외의 주소로 발송이 안 되는 제약이 있어, 팀원들이 각자 이메일로 가입 테스트를 할 수 없었기 때문이다. 현재는 Supabase Auth의 "Confirm email"을 끈 상태에서 이메일+비밀번호로 즉시 가입하는 방식이며, 실제 서비스로 전환할 때는 이메일 인증 여부를 다시 검토해야 한다.
