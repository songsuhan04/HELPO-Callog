# 아키텍처

![Callog 아키텍처](아키텍처.svg)

굵은 화살표가 이 구조에서 가장 주의할 지점이다. 브라우저가 Postgres를 직접 질의하기 때문에,
**접근 통제가 전부 RLS 한 겹에 걸려 있다.**

## 어르신은 계정이 없다

이 설계가 나머지를 결정한다. 어르신은 가족이 보낸 링크(`/e/:token`)를 한 번 누르면 들어온다 —
회원가입도 비밀번호도 없다. 온보딩 마찰을 없애려고 택한 구조이고, 대가로 두 가지가 따라온다.

- **인증 주체가 토큰 하나다.** 토큰이 새면 그 어르신의 기록이 열린다. 그래서 토큰은 초대 화면을
  방문할 때마다 새로 발급된다.
- **통제가 RLS에 집중된다.** 보호자는 Supabase Auth 세션을 갖지만 어르신은 없으므로,
  1가족 : N어르신 경계를 Postgres 정책으로만 지켜야 한다. 정책이 뚫리면 다른 가족의 건강 정보가 보인다.

## 데이터가 흐르는 두 경로

| 경로 | 주체 | 권한 |
| --- | --- | --- |
| 브라우저 → Postgres | `supabase-js` 직접 질의 | anon 키 + **RLS로 통제** |
| Serverless Function → Postgres | `service_role` | **RLS 우회** |

서버 함수가 RLS를 우회하므로, 함수를 아무나 부를 수 있으면 통제가 의미를 잃는다.
크론 엔드포인트 인증(`lib/cronAuth.ts`)이 "설정이 빠지면 닫히는 쪽"으로 실패해야 하는 이유가 이것이다.

## 크론이 두 갈래인 이유

| 트리거 | 주기 | 하는 일 |
| --- | --- | --- |
| GitHub Actions | 매시간 | `check-no-response` — 무응답 어르신 확인 후 보호자에게 Web Push |
| Vercel Cron | 하루 1회 | `cleanup-old-letters` — 보관 기간 지난 파일 삭제 + 다음 날 안부 질문·주제 미리 생성 |

Vercel Hobby 플랜은 크론을 하루 한 번만 돌린다. 그래서 안부 시각이 08:00인 어르신은
7시간째인 15:00이 아니라 21:00에야 알림이 갔다 — 임계값은 7시간인데 실제로는 13시간이 걸린 셈이다.
**임계값을 낮추는 대신 집행 주기를 고쳐** 7시간을 그대로 두고도 약 6시간 빨라졌다.
근거와 한계는 [근거자료-임계값.md](근거자료-임계값.md) 참고.

`cleanup-old-letters`가 파일 정리와 질문 생성을 함께 하는 것도 같은 제약 때문이다 —
크론 개수를 늘리는 대신 하나에 묶었다.

## 외부 의존

- **Google Gemini** — 음성 분석(발화 유무·침묵 비율·소견), 지병 맞춤 안부 질문·주제 생성.
  모델이 예고 없이 폐기돼 조용히 fallback으로 실패한 적이 있어, 지금은 실패 상태를 명시적으로 기록한다.
- **Web Push (VAPID)** — 보호자 알림. VAPID 키가 없으면 조용히 아무것도 하지 않는다.
- **Resend** — 현재 호출 경로가 없다. 도메인 인증을 받지 못해 이메일 인증을 제거했다
  ([기능설계서 §2.6](기능설계서.md)).

## 보관 정책

영상편지 7일, 음성 30일(받아쓴 내용은 남는다). 만료된 파일은 위 일일 크론이 지운다.
영상편지에는 **어떤 AI 분석도 하지 않는다** — 개인정보 측면에서 범위에서 제외했다.
